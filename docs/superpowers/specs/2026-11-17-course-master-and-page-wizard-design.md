# 便覧が持つ科目を「番号で決まらないものだけ」にし、科目名簿を courses テーブルへ移す 設計

2026-11-17 / 対象ブランチ: `feature/curriculum-import`
前提: [2026-11-13 下書き編集画面の簡素化](2026-11-13-requirements-review-simplification-design.md) の続き。
あの簡素化で入れたツリー・枠・チップ・`claim_rule_box?` はそのまま使う。

## なぜ直すのか

ユーザーの言葉（8件）:

> * PDF読み取りは１ページずつ表示して、読まない、科目表、要件表の3択を選ばせる様にする。最後に一覧で確認できる様にする
> * 確認後にすぐ読み取れる様にする
> * 読み取り中なことをわかりやすくしたい。
> * 科目はもともと保存されているものを参照したいのですが、現在の使用がどうなっているのか
> * 科目番号・科目名が同じ場合は重複しても外す(同じ科目表を読み込んでも止まらない)
> * 科目の規則は人が読んでも直感的に理解しづらいので、表示させない
> * 区分名に英語の識別子が使われているのがわかりづらいので、UIでは表示させない
> * 科目表はここで取り込むのではなく、知能情報アドバンストなどの科目番号で判定できないもののみ登録させる仕組みにする

会話で絞り込んだ意図:

- 科目表は「既存の仕組みだけでは区別できない科目を登録するために使いたい」。読むのはやめない。
- 番号で判定できない科目は、科目表から来るのが自然。
- 工学融合は科目番号で識別可能（ユーザーからの訂正）。
- 科目マスタは、実運用では時間割PDFの取り込みから埋まる。

### 実測した事実

**1. 484科目のうち、区分が科目番号から決まるのは8割以上。**

2024年度の便覧（`config/curricula/intelligent_informatics/2024.json`）の484科目を科目番号で仕分けた。
（番号で決まっても外せない科目がこのあと見つかる。外国語71件は言語の欄のために残す。§3 を参照。実際に残るのは175件。）

| | 科目数 | 区分が番号から決まるか |
|---|---:|---|
| 共通教育（健・人・社・自・総・C・琉・外1・外2〜7） | 322 | **決まる**（`number_patterns` が既にある） |
| 専門のうち番号帯が区分と1対1 | 79 | **決まる**（パターンが未設定なだけ） |
| 専門のうち番号帯に複数の区分が混在 | 81 | **決まらない** |
| 科目番号なし | 2 | 決まらない |

「決まる」79件の内訳: 先0〜先5→専門基礎科目(22)、知能4→知能情報関連(10)、知能9・機械9・社基9・エネ9・電気9・建築9・電情9→工学融合科目(38)、転0〜転2→専門基礎科目(6)、情0→算入対象外(1)、情1→日本語表現法入門(1)、全教4→知能情報関連(1)。

「決まらない」81件の内訳:

| 番号帯 | 科目数 | 混ざっている区分 |
|---|---:|---|
| 知能1 | 3 | 情報技術系（必修）2 / 数学基礎（必修）1 |
| 知能2 | 19 | コア（必修）9 / アドバンスト4 / 研究・基礎演習・実験（必修）4 / 総合力演習（必修）1 / 関連1 |
| 知能3 | 15 | アドバンスト14 / 研究・基礎演習・実験（必修）1 |
| 工共1 | 8 | 総合力演習（必修）2 / 数学基礎（必修）2 / 関連3 / コア（必修）1 |
| 工共2 | 4 | 数学基礎（選択）3 / コア（必修）1 |
| 工共3 | 20 | 関連17 / 総合力演習（必修）1 / 研究（必修）1 / コア（必修）1 |

必修31科目は、すべてこの「決まらない」帯の中にある。つまりユーザーの言う「知能情報アドバンストなど」は、**知能2・知能3・工共1〜4 の81件**のことで、ここだけ人が登録すればよい。

**2. いま科目表は2つの仕事を掛け持ちしている。**

- **判定のための分類** — 区分・必修・役割・承認が要るか。
- **学生のメニュー** — 履修計画の「便覧から選択」が `selectable == true` の科目を並べる（[_add_course_box.html.erb:4](../../../app/views/plans/_add_course_box.html.erb)）。学生の卒業要件画面の科目表も同じ配列から描く（`requirements_helper.rb#courses_by_category`）。

2つ目があるせいで、484件を減らせないでいた。

**3. 科目の実体は、すでに `courses` テーブルにある。**

`courses`（`course_number`・`name`・`credits`）は、時間割PDFの取り込み（[importer.rb:87](../../../lib/timetable_import/importer.rb)）、デモデータ、学生の自由入力で埋まる。履修も予定も `courses` の行を指している。履修計画の追加も、便覧の番号から `Course.where(course_number:, name:)` を引いて `Course` の行を予定に入れている（[plan_courses_controller.rb:62](../../../app/controllers/plan_courses_controller.rb)）。
**便覧側の484件は、`courses` の写しに区分の札を貼ったものでしかない。**

ただし現状は向きが逆で、デモでは便覧の484件から `courses` を作っている（[demo_data.rb:46](../../../app/services/demo_data.rb)）。

**4. 「科目が1件もない」検査が、この変更と正面からぶつかる。**

`rule_checks.rb:74` が「数える区分に科目が1件もない → この規則は必ず不足になります」と警告する。ユーザーが「表示させない」と言った規則の正体はこれで、画面にはこう出ている:

```
確認  規則: rule_ge_total
数える区分(ge_health_sports、ge_humanities、ge_social_sciences、…)に科目が1つもありません。
この規則は必ず不足になります。
```

いまは科目表を読む前だから出ている。ところが本設計を入れると、`ge_humanities` のような番号で決まる区分は**正しく0件になる**ので、この警告が全区分ぶん永久に出続ける。同じ前提の検査が他に2つある（`display_checks.rb:108`、`document_checks.rb:14` は科目0件で公開を止める）。隠すのではなく、前提のほうを直す。

**5. 同じ科目表を2回読むと止まる。**

`DraftMerge#courses` は、別のページの科目と同じ番号でも上書きせず別の key で足す。その結果 `CourseChecks#duplicate_numbers` が「公開すると便覧を読み込めません」と公開を止める。ページ範囲が重なる便覧や、指定を間違えて読み直した場合に起きる。

**6. 手順①は、1ページずつ見られない。**

全ページの行が縦に並び、幅16pxのサムネイルだけが頼り。種別を選んだら `ページの指定を保存` で画面全体が再読み込みされ、そのあとで「読む」を押す2段構え。読み取り中の表示は `<p>` 1行のテキストだけ。

## ゴール

- 便覧が持つ科目を、**番号から区分が決まらないものだけ**にする（2024年度で484件 → 175件。実装後に実測）。
- 学生のメニューと学生向け科目表が、`courses` テーブルから描かれる。
- 同じ科目表を2回読んでも止まらない。
- 突き合わせの指摘に、`rule_ge_total`・`ge_humanities` のような内部の識別子が出ない。番号で決まる区分が0件であることを、問題として報告しない。
- 手順①が、1ページずつ大きく見て3択を選び、最後に一覧で確かめ、そのまま読み取りに入る流れになる。
- 読み取り中であることが、ひと目で分かる。

## 非ゴール

- **判定の数式を変えること。** 同じ便覧・同じ履修なら、学生に出る判定結果は前後で同じ。
- 認証。取り込みは引き続き `/requirements` に置く。
- 時間割PDFの取り込み側の作り直し。`courses` がそこから埋まる前提に乗るだけ。
- 公開済みの便覧の形（`PublishedDocument` が通す欄）を減らすこと。484件を持つ既存の便覧も、そのまま読めて判定できる。
- 他学部の便覧で実際に通ることの確認。

## 失敗とみなすもの（アンチゴール）

- **科目を落としたせいで、判定が「卒業できます」に傾くこと。** 落としてよいのは、番号からも同じ区分に決まると確かめられた科目だけ。読み取った区分とパターンの区分が食い違う科目は、**必ず残す**（それが例外だという証拠だから）。
- **必修・役割・承認・「選べない」の印が、科目と一緒に消えること。** これらは番号からは絶対に分からない。印が1つでも付いていれば残す。
- 学生の履修計画から、いま選べている科目が選べなくなること。
- `test/fixtures/files/graduation_golden_2024.json` が変わること。変わったら設計か実装が間違っている。
- 「触らずに保存しても、文書が1バイトも変わらず、人が確認した印も付かない」が壊れること。

## 検討した作り

**(イ) 文書は484件のまま、確認画面だけ短くする。** いちばん小さく、学生の画面に触らない。ただし「登録するために使いたい」に答えていない。公開する文書も重複の問題も減らない。採らない。

**(ウ) 科目表の2つの仕事を、どちらも便覧の中で分ける。** 読んだ全科目を「メニュー用の軽い一覧」として残し、区分・必修・役割を持つ「登録」は例外だけにする。学生の画面に触らずに済むが、便覧の中に2種類の科目リストが並び、`courses` との三重の写しになる。採らない。

**(ア) 便覧は例外だけ持ち、科目名簿は `courses` テーブルに置く。**（採る）
`courses` は既に履修・予定・時間割取り込みの正本で、便覧の484件はその写しだった。写しをやめる。
ユーザーがこの形を選択済み。

## 決めたこと

### 1. 科目名簿（CourseDirectory）

「この便覧で、この区分にはどの科目があるか」に答える口を1か所作る。`app/services/course_directory.rb`。

入力は、便覧の文書（`categories` の `number_patterns` と、登録された例外科目）と `Course` の行。

```ruby
directory = CourseDirectory.new(document)
directory.in_category('ge_humanities')  # => [CourseDirectory::Entry, ...]
directory.category_for(number)          # => 区分キー or nil
```

1件は `number`・`name`・`credits`・`category`・`required`・`roles`・`requires_approval`・`selectable` を答える。決め方:

1. 便覧の `courses` に同じ番号の登録があれば、**その登録を正**とする（区分・必修・役割・承認・選べるかを持つ）。名前と単位は `Course` の行があればそちらを使い、無ければ登録の値を使う。
2. 登録が無ければ、`Course` の番号を `Catalogue#pattern_category_for` に掛けて区分を決める。決まらない `Course` は名簿に出さない。
3. 2で出た科目は `required` も `roles` も `requires_approval` も持たず、`selectable` は真とする。

`Course` を引く範囲は、`course_number` が空でない全行。学部ごとの絞り込みはしない（番号のパターンが学部を決めている）。

**判定（`GraduationAssessment`）は、この名簿を使わない。** 判定はいまどおり `Catalogue` と `EntryNormalizer#pattern_course` の経路で動く。名簿は「人と学生に、どんな科目があるかを見せる」ためだけのもの。判定の数式を変えないという非ゴールを、構造で守る。

### 2. 便覧に残す科目の決め方（絞り込み）

絞り込みは `DraftMerge#courses` が、読み取りの結果を文書に入れるときに行う。`app/services/curriculum_import/course_filter.rb`。

読んだ科目を、**次のいずれかに当たれば残す**。どれにも当たらなければ入れない。

- 科目番号が空、または `pattern_category_for` が区分を決められない
- パターンが決めた区分と、読み取った区分が**違う**
- `required` が真
- `roles` が空でない
- `requires_approval` が真
- `selectable` が偽
- `review_reason` がある（AIが要確認と言った科目）

「違えば残す」が安全弁になっている。パターンが間違っていても、科目が黙って消えることはない。

落とした件数と内訳は、そのページの `warnings` に残して画面に出す:

> 番号から区分が決まる科目 274件は、登録しませんでした（区分「人文系」54件、「総合科目」74件、…）。区分の科目番号のパターンで数えます。

`selectable` が偽の5件（自コース提供の工学融合）は、この規則で残る。

### 3. 番号パターンの提案

絞り込みが効くには、専門区分にも `number_patterns` が要る。2024年度の便覧は共通教育の9区分ぶんしか持っていない。

科目表のページを読んだあと、読めた科目から番号帯と区分の対応を作り、**まだパターンを持たない区分に提案する**。対応を作る仕組みは `CurriculumImport::CategoryInference` が既に持っている（`by_hundreds` / `by_prefix`）。

- 百の位までの鍵（`知能4`）が1区分にしか現れず、根拠が `CategoryInference::MIN_SUPPORT`（3件）以上あれば、その鍵をその区分のパターンとして提案する。
- 接頭辞だけの鍵（`先`）でも同じ条件で提案する。百の位の鍵で提案済みの区分は重ねない。
- 複数の区分にまたがる鍵（`知能2`）は提案しない。
- 提案は、要件表の確認画面の区分の欄に「科目番号のパターンの候補: 知能4、知能9」として出し、**人が押して採用する**。黙って入れない。パターンは科目表に載っていない科目まで区分に数えるので、人が見ていない推測を判定に入れない。
- 採用すると、その場で絞り込みが走り直し、該当する科目が確認画面から消える。消えた件数を知らせる。

2024年度の実データで候補に出るのは `先0`〜`先5`（→専門基礎科目）、`知能4`（→知能情報関連）、`知能9`・`機械9`・`エネ9`・`電気9`・`電情9`・`建築9`・`社基9`（→工学融合科目）。
`転`・`全教4`・`情0`・`情1` は根拠が `MIN_SUPPORT`（3件）に届かず、候補に出ない。該当する9件は登録したまま残る。

この提案をすべて採用したときに便覧へ残るのは **175件**（実測。英語以外の外国語57・関連32・アドバンスト18・英語14・コア12・研究10・専門基礎9・工学融合5・総合力演習4・数学基礎必修3・数学基礎選択3・人文系3・情報技術系2・日本語1・算入対象外1・琉大特色1）。

**外国語の科目71件が残るのは、言語が科目番号から決まらないから。** 便覧の `foreign_language` 規則は
`grouped_max` の `group_by: "field:language"` で、「同じ一外国語で4単位」を言語ごとに分けて数える（`Ledger#grouped_credits_by`）。
番号から決まるのは区分までで、どの言語かは決まらない（`外7xx` は1つの言語ではない。だから `english_plus_two_7xx_languages`
のケースがある）。科目を外すと、判定は番号から区分だけを復元した合成科目（`EntryNormalizer#pattern_course`）を見るので、
`language` の欄が空のまま「言語の欄が未確認」になり、充足とも不足とも言えなくなる。2024年度の便覧で実際に測ると、
ドイツ語・フランス語・中国語などを修得した学生の判定が `satisfied` から `needs_review` に落ちた。

そこで §2 の残す条件に、**「便覧の規則が欄で分ける科目は残す」** を足す（`CourseFilter#grouped_field?`）。
欄の名前はコードに持たない。文書の `rules` をたどって `grouped_max` の `group_by` が `field:` で始まるものを集め、
その欄に値を持つ科目を残す。入れ子（`any_of` の `options`・`all_of` の `conditions`）の中の規則もたどる
（2024年度の `foreign_language` は `any_of` → `all_of` の中にある）。`language` を直書きすると、別の欄で分ける便覧が
来たときに同じ穴が開く。2025年度の便覧には `grouped_max` が無いので、この条件は1件も残さない。

**順番の依存に注意。** 要件表→科目表の順に読む流れは既に強制されている（`read_pages_controller.js#readAll`）。要件表が区分を作り、科目表がパターンの候補を出す。パターンが空のまま科目表だけ読むと何も落ちないが、壊れはしない（いまと同じ484件になるだけ）。

### 4. 重複を外す

`DraftMerge#courses` で、**科目番号と科目名の両方が既にある科目と一致する行は、足さない。** 比較は `CourseNumber.normalize` した番号と、`squish` した名前で行う（全角・空白の揺れを同じと見る）。

落とした件数はそのページの `warnings` に残す:

> 同じ科目番号・科目名の科目 12件は、既にあるので足しませんでした。

`CourseChecks#duplicate_numbers` の「公開を止める」指摘はそのまま残す。番号が同じで**名前が違う**行は、本物の読み違いなので止め続ける。

### 6. 手順①の作り直し

`/curricula/:id` の中に留める（別URLのウィザードにはしない。②③④と同じ1枚という形を崩さない）。

**6-1. 1ページずつ見る**

```
┌ ① PDFを読み取る ─────────────────────────────────┐
│                                                        │
│   ┌──────────────┐    3ページ目 / 全58ページ          │
│   │              │                                    │
│   │  ページ画像   │    このページは                     │
│   │  （大きく）   │     ( ) 読まない                    │
│   │              │     (•) 要件表                      │
│   │              │     ( ) 科目表                      │
│   └──────────────┘                                    │
│                                                        │
│   [← 前へ]  [次へ →]        指定済み 3 / 58           │
│                                                        │
│   ▸ 全ページを一覧で見る                                │
└────────────────────────────────────────────────────────┘
```

- 画像は、PDFペインが使っている実寸（`page_image_width`）に合わせて、横600px程度で出す。
- 種別を選ぶと**その場で次のページへ進む**（`読まない` も含む）。保存の送信はしない。
- 選んだ結果はクライアント側に持ち、一覧で「この指定で読み取る」を押したときに1回だけ送る。
- キーボードの左右で前後、1/2/3 で種別を選べるようにする。58ページを捌く作業なので、マウスだけにしない。
- 画像が無い下書き（ページ数を手で指定した場合）は、ページ番号と、取り出したテキストの冒頭200字を代わりに出す。

**6-2. 最後に一覧で確認する**

最後のページで「次へ」を押すと一覧に変わる。途中でも「全ページを一覧で見る」から開ける。

```
  指定の確認                           要件表 4 ・ 科目表 6 ・ 読まない 48

  [サムネ] 1ページ  読まない                     [直す]
  [サムネ] 2ページ  読まない                     [直す]
  [サムネ] 3ページ  要件表                       [直す]
  ...

  [この指定で読み取る（10ページ）]
```

- 「直す」はそのページの1枚表示に戻る。
- 読み取りの結果を持つページの種別を替えていれば、いまと同じ警告をここで出す（`saved_notice` の文面を流用）。
- 人が直した規則・章・行があるページを読み直すときの確認（`RereadWarning`）も、ここで一度に見せる。

**6-3. 確認したらそのまま読み取る**（②）

「この指定で読み取る」の1回の操作で、`PATCH /curricula/:id`（指定の保存）→ 読み取りの開始、までを続けて行う。いまのように画面が再読み込みされて「読む」を押し直す段を無くす。

実装は、保存を `fetch` で送って成功を待ち、そのまま `read-pages` コントローラの `readAll` に入る。保存が失敗したら読み取りに進まず、理由を一覧の上に出す。サーバー側の `update` は、Turbo Stream でも応答できるようにする。

読み取りそのものの作りは変えない。1ページずつ順に、要件表を先に、同期で呼ぶ。

**6-4. 読み取り中を分かるようにする**（③）

```
  読み取り中  ━━━━━━━━━━━━━━━━░░░░░░░░  6 / 10 ページ

  ✓ 3ページ  要件表   読み取り済み
  ✓ 4ページ  要件表   読み取り済み
  ⟳ 11ページ 科目表   読み取っています…（0:42）
    12ページ 科目表   待機中
```

- 進捗バーと「n / m ページ」。
- いま読んでいるページの経過秒数を出す（1ページで数十秒かかり、再試行を含めると数分になる。止まって見えるのを防ぐ）。
- 読み取り中はページの一覧を出したまま、終わった行から状態を替える。
- 読み取り中は、`② 要件表を確認する`・`③ 科目表を確認する`・`④ 公開する` の節を薄くして触れなくし、「読み取りが終わると出ます」と出す。いまは古い内容のまま触れてしまい、保存で弾かれる。
- 終わったら「読み取りが終わりました。要件表の確認へ」のボタンを出し、押すと画面を開き直して②へ飛ぶ。

### 7. 学生の画面

便覧の `courses` を直接読んでいる4か所を、名簿（CourseDirectory）に向ける。

| 場所 | いま | これから |
|---|---|---|
| `_add_course_box.html.erb:4` 「便覧から選択」 | 便覧の `courses` から `selectable` を抜く | 名簿の `in_category` から、修得・予定済みの番号を除く |
| `plans_controller.rb:38` `@catalogue`（検索・一覧） | 同上 | 名簿を区分と検索語で絞る。`@persisted_numbers` は名簿が `Course` 由来なので不要になる |
| `requirements_helper.rb#courses_by_category` 学生の科目表 | 便覧の `courses` を区分で束ねる | 名簿を区分で束ねる |

**学生の科目表の説明文を直す。** 「この便覧に載っている科目です」は正しくなくなる。「あなたのコースで履修できる科目です」に替え、件数の下に「科目番号のパターンで数える科目を含みます」と添える。

### 8. デモと種まき

デモの `courses` が便覧から作られている（`DemoData#import_courses`）経路を切り離す。

- 科目名簿の種として `db/course_master.json`（`number`・`name`・`credits` の配列）を置く。中身は、いまの2024年度・2025年度の便覧の科目から作る（重複は番号と名前で1件にまとめる）。
- `DemoData` は、便覧の `document['courses']` ではなくこのファイルから `Course` を作る。
- 既存の便覧JSON（`config/curricula/.../2024.json`・`2025.json`）の `courses` は**減らさない**。公開済みの便覧の形を減らさないという非ゴールを守る。名簿は「便覧の登録 → `Course` + パターン」の順で引くので、484件を持つ便覧でもいまと同じ結果になる。

実運用では、学部の事務の人が年度の時間割PDFを先に取り込み、`courses` を埋めてから便覧を登録する。この順番を、取り込みフォームの説明に1行で書く。

## 残る制約

- **時間割を取り込んでいない年度は、学生のメニューが薄くなる。** 名簿は `courses` にある科目しか出せない。取り込み前は、学生は「自由入力」で足すことになる（いまもその経路はある）。取り込みフォームと学生のメニューの空のときの文面で、このことを言う。
- **番号パターンは推測である。** 「知能4は知能情報関連」は、便覧に載った10科目から言っているにすぎない。載っていない知能4xxの科目が別の区分なら、間違った区分で数える。だから提案は人が押して採用する形にし、黙って入れない。
- 判定の経路（`EntryNormalizer#pattern_course`）は前からこの推測に乗っている。本設計はその範囲を広げる。広げたぶん、区分の取り違えが「要確認」ではなく「充足」に化ける余地が増える。提案を人が承認する一手を必ず挟む理由がこれ。

## レビューで塞いだ穴

設計書をレビュー役に読ませて出た6点。すべてここで決める。

### R1. 絞り込みは、人が触った科目を黙って落とさない

§2 の残す条件に、次を足す。

- `confirmed` が真（人が PDF と見比べて確認した）
- `added_by_hand` が真（人が手で足した）
- 承認の注記が当たっている

このアプリは一貫して「人が触ったものは、読み直しでも外さない・上書きしない」を守っている（`DraftMerge`・`CourseEdit`・`RereadWarning`）。絞り込みだけ逆向きにはしない。

ただし **§3 のパターン採用のときは別** にする。あれは人が「この番号帯はこの区分だ」と押す操作なので、落ちる件数を見せたうえで、確認済みの科目も落としてよい。

> 採用すると、知能4・知能9…の274件を便覧から外します。うち18件は確認済みです。外しますか。

この区別がないと、複製した下書き（`Duplicate` が `confirm_all!` で全件を確認済みにする）は1件も減らない。

読み取り時に落とした科目は `removed_by_human` に記録しない。同じ条件が次の読み取りでも効くので、戻ってこない。

### R2. 名簿に載せる `Course` の範囲

`course_number` が空でない行のうち、**`Course#custom?`（学生の自由入力で作られた行）を除く。** それ以外の絞り込みはしない。

- 自由入力の行を入れると、ある学生が打ち間違えた番号が、全学生のメニューと学生向け科目表に並ぶ。`custom_category` を持つ行は、その学生の計画の中だけのもの。
- 過年度・他学科の行は入れる。`CourseOffering` で開講年度に絞ることはしない。いまの便覧由来のメニューも「開講されているか」は見ていないので、絞らなくても後退しない。絞ると、`db/course_master.json` から種まきしたデモに `CourseOffering` が無く、メニューが空になる。
- 件数は、区分ごとに出すぶんには問題ない（2024年度で最大74件）。`plans_controller.rb#load_catalogue` の `@catalogue`（検索・一覧）だけ、`Course` 全件が入りうるので **200件で打ち切り、「絞り込んでください」と出す。** 既に検索欄がある。

### R3. 「便覧から選択」が送る値は `Course#id` にする

名簿の1件は `Course` の行そのものを指すので、フォームの value を `course_number` から `Course#id` に替える。同じ番号で名前の違う行（2024年度と2025年度の「知能212」のような実例がある）があっても、どの行かが決まる。

`plan_courses_controller.rb#find_catalogue_course` の「番号＋便覧の名前で引いて、2行以上なら `AmbiguousCourse`」は不要になるので外す。代わりに、受け取った id の `Course` が名簿にあり `selectable` であることだけ確かめる。`@unavailable_numbers`（修得・予定済み）は番号のまま突き合わせる。

`custom_course` の経路（自由入力）は変えない。

### R4. 絞り込みで判定が変わらないことを、テストで押さえる

`graduation_golden_2024.json` は守ってくれない。golden が読むのは `config/curricula/.../2024.json`（484件のまま）で、ケースの履修もそこから作るので、絞り込みを入れても定義上一致する。

専用の回帰テストを足す。**同じ履修を、絞り込み前の文書と絞り込み後の文書の両方で判定し、結果が一致することを確かめる。**

- 入力は 2024年度の便覧（484件）と、§3 の提案をすべて採用した文書（175件）。
- 履修は golden のケースをそのまま使う。落ちる309件の科目を含むケースが要る（デモ学生の履修48件には、落ちる科目が7件ある）。
- 比べるのは、区分ごとの算入単位・総単位・各規則の充足/不足/要確認。

この設計でいちばん怖い変更なので、無検査では通さない。

### R5. 手順①の警告は、保存の応答で返す

一覧の「この指定で読み取る」は、まず指定を保存する。サーバーは保存のあと、Turbo Stream で一覧を描き直し、**警告（種別を替えたページの結果を外した旨、`RereadWarning`）を一緒に返す。**

- 警告が無ければ、画面はそのまま読み取りに入る。操作は1回。
- 警告があれば、その場で確認を出し、人が押したら読み取りに入る。押さなければ指定は保存されたまま止まる。

保存前の指定から警告を作るプレビューの口は作らない。警告は保存済みの `document` と `pages` から作るもので（`RereadWarning.for(document, page)`）、保存前の状態で正しく作るには同じ判断をクライアントに持たせることになる。ユーザーが無くしたいと言ったのは「画面が丸ごと再読み込みされて、読むボタンを押し直す」ことで、失われるものを知らせる確認ではない。

`curricula_controller#update` を Turbo Stream に応答させる。いまは `redirect_to` のみ。

### R6. 既にある下書きと、複製した下書きも絞り込める

絞り込みを読み取り時だけに置くと、作業中の下書きと `Duplicate` で作った下書きは484件のまま公開される。年度が替わるたびに484件の便覧が再生産される。

**③ 科目表を確認する の節に「番号で決まる科目を外す」ボタンを置く。** 中身は §3 のパターン採用と同じ操作で、押すと件数を見せて確認し、条件に当たる科目を外す。読み取りを経ていない下書きにも効く。

### R7. 2025年度の便覧は、この設計では変わらない

`config/curricula/intelligent_informatics/2025.json` は `number_patterns` を1つも持たず、科目も99件（すべて専門）。パターンが無いので絞り込みは1件も落とさず、名簿の「パターンで `Course` を拾う」も効かない。2025年度の学生のメニューは、いまの99件のまま。

壊れではない（便覧に登録された科目は名簿が最優先で出す）。受け入れ条件に「2024年度で175件に減ること」は書くが、「2025年度で減ること」は書かない。2025年度にパターンを入れるかどうかは、この設計の外。

## ビルダーに委ねること

- `CourseDirectory` のキャッシュ。学生の画面1回で何度も引くので、リクエストの中で1つを使い回す形にする（`CurriculumChoices` と同じ考え方）。`Course` の全件読みが重ければ、番号の接頭辞で絞る。
- 1ページずつの画面を、Stimulus 1つで作るか2つに割るか。既存の `read-pages` コントローラとの分け方。
- 進捗バーの刻み（ページ単位でよいか、経過時間も混ぜるか）。
- `db/course_master.json` の作り方（1回限りの rake タスクで生成してコミットするか、スクリプトを残すか）。
