# 便覧PDFから卒業要件を読み取り、確認して保存する

2026-10-29 / 対象: 「卒業要件の確認」画面（便覧の取り込み）、`GraduationAssessment` 一式、
`CurriculumRepository`、学生側の表示

## なぜ作るか

いま卒業要件は2か所に分かれて入っている。

1. **科目表** — `config/curricula/intelligent_informatics/2024.json` の484科目。全部手で入れた。
2. **判定ロジック** — Rubyの定数。`Catalogue::REQUIRED`（区分と必要単位）、`Catalogue::CATEGORIES`（区分の語彙）、
   `SpecialistChecks` の57・22・37、`Evaluation` の130、`CommonChecks` の30・14・12・2、
   `Ledger#apply_natural_cap` の「自然系は上限2単位」、`Catalogue#exclusion` の「自コース提供の工学融合は算入不可」。

1は便覧1冊につき手入力が丸ごと要る。2はコードなので、年度やコースが変われば書き換えるしかない。

便覧を2冊（2024年度・2025年度、どちらも知能情報コース）並べて比べると、数字だけでなく
**区分の名前そのものが変わっている**。

| | 2024年度 | 2025年度 |
|---|---|---|
| 卒業算入の総単位 | 130 | 124以上 |
| 共通教育 | 30（健康運動系・人文系・社会系・教養／総合領域） | 34以上（基盤領域・教養領域） |
| 専門 | 必修57 ＋ 選択37（うち内数22） | 90以上（必修＝コース専門31＋工学共通38、選択21以上） |

`Catalogue::CATEGORIES` は2024年度の区分名を並べた固定リストなので、2025年度の便覧はそもそも載らない。
他学部ならなおさら合わない。

作りたいのは、便覧PDFを「卒業要件の確認」画面から上げると科目表と判定ロジックの下書きがAIで埋まり、
人が見て直して保存する、という流れ。年1回、学部の事務の人が使う。

## ゴール / 非ゴール / アンチゴール

**ゴール**

- 便覧PDFを上げると、科目表（どの科目がどの区分か）と判定ロジック（区分ごとの必要単位と特例）の下書きができる。
- 下書きを画面で確認・修正して保存すると、**そのPDFと同じ要件で判定が動く**。
- 2024年度と2025年度の便覧が、どちらも同じ画面から通る。
- 2024年度は、いま手で入れたJSONと同じ判定結果になる（今の挙動を壊さない）。
- 判定ロジックがコースや年度ごとのRubyコードではなくデータになっていて、他コース・他学部の便覧も
  同じ画面から入れられる形になっている。
- **学生が見る画面も、その学生の便覧から描かれている。** 章の見出し、区分の和名、必要単位、
  卒業総単位が、2024年度の決め打ちではなくなっている。
- AIが使えないときでも、同じ画面で手入力して保存できる。

**非ゴール**

- 認証。取り込みは学生も開ける `/requirements` に置くので、認証が入ったら学生から隠す必要がある。
  それは今回やらない（後述の「残る制約」）。
- 便覧PDFの保管。確認が済んだらPDFもページ画像も消す。`timetable_uploads` と同じ扱い。
- 外国人学生の特例、編入・転学科の個別認定（READMEで判定対象外と決めている）。
- 1冊を全自動で、人の確認なしに保存すること。
- 他学部の便覧で実際に通ることの確認。形としては受け入れるが、通ることを確かめるのは2024・2025の2冊。
- 便覧の全ページを読むこと。読むのは科目表と要件表のページだけ。

**アンチゴール**

- **読み間違いが「卒業できます」になること。** 単位が本来と違う区分に入る、または算入されないまま充足と出る。
  とくに難所は、外国語の二択・自然系の上限・微分積分の系列選択・自コース提供工学融合の除外・指導教員の承認。
- 読めなかった、わからなかったところが黙って通ること。わからないときは必ず要確認にする。
- 無料枠のAPIが止まったときに、取り込みの仕組みごと使えなくなること。

## 決めた形（画面）

モックで本人が触って決めた形（使い捨て。`.superpowers/brainstorm/30815-1793091649/content/` にある）。

### 1. 置き場所は「卒業要件の確認」タブ。取り込みボタンを足す

新しいタブや管理者エリアは作らない。既にある `/requirements` に取り込みを足す。
講義登録とまったく同じ形にする。

- `/course_registrations`（講義登録）に時間割PDFのアップロードフォームがあり、
  確認画面は `/timetable_uploads/:id` という別のルート。
  確認画面にいる間もナビは「講義登録」が光ったまま（`app/views/shared/_nav.html.erb`）。
- 便覧も同じ。`/requirements`（卒業要件の確認）に取り込みのフォームを置き、
  確認画面は `/curricula/:id`。その間もナビは「卒業要件の確認」が光ったまま。

`/requirements` に出すもの:

1. **いまの便覧**（その学生の入学年度のもの）。`display` と `rules` を描く読み取り専用の表示。
2. **便覧の一覧**。公開済みと下書き。下書きは「確認中」として確認画面へのリンクを出す。
3. **取り込みのフォーム**。学部名・コース名・slug・入学年度とPDF。

ルートは `timetable_uploads` にそろえる。

```ruby
resources :curricula, only: %i[create show destroy] do
  member do
    post :publish
    post 'pages/:page/read', action: :read_page, as: :read_page
    patch :update_courses
    patch :update_rules
    get 'page_image/:page', action: :page_image, as: :page_image
  end
end
```

### 2. 確認画面（`/curricula/:id`）は1枚、3段

時間割の確認画面と同じく1つのURLにまとめ、上から順に開く。

**ページの指定** — 1ページずつ「科目表」「要件表」「読まない」を選ぶ。既定は「読まない」。
便覧はコースや年度で構成が違うので、どのページを読むかは人が決める。自動判定しない。
行ごとに「読む」ボタン、上に「全部読む」（§3）。

**PDFを並べて見られるようにする。** 時間割の確認画面に入れた貼り付くPDFペイン
（`docs/superpowers/specs/2026-10-20-timetable-upload-pdf-pane-design.md`）を、そのまま使う。
原本と見比べながら直す作業は同じで、便覧のほうが行数が多いぶん効く。

### 3. 要件表の確認（先）

読む順は **要件表 → 科目表**。要件表が区分の一覧を決め、科目表はその区分に科目を割り当てるため。

- 区分ごとの必要単位の表。区分名・必要単位・確認チェック。
- 注釈は1つずつカードで出し、どの型に割り当てるかを選ばせる（型は下の7つ）。
  割り当てないものは「判定に反映しない」として残し、記録だけする。
- 判定に落とせない注釈（指導教員の承認、外国人学生の特例）は赤で出し、理由を書く。

### 4. 科目表の確認 — 区分ごとにまとめた並び

**本人が選んだ形（B）。** PDFの行順ではなく、区分ごとにまとめて出す。

- 区分の見出しに「区分名・科目数・必修単位」を出す。要件表の数字とその場で突き合わせられる。
- 区分のなかで浮いている科目（他の科目と科目番号の付き方が違う、など）には印と理由を付ける。
- 読み落とした科目を手で足せる。`timetable_upload_rows` の `added_by_hand` と同じ扱い。
- 各行は確認チェックを持ち、押した時点で保存する（既存の確認画面と同じ）。

区分の取り違えがこの画面のいちばん怖い間違いで、PDFの行順に並べると正しい行に埋もれてしまう。
区分ごとにまとめれば、科目数と必修単位が要件表と合わないことで気づける。

### 5. 判定に反映できない条件の出し方（F）

- **本人が答えられるものは学生に聞く。** 「他学部提供の情報系科目の履修登録には指導教員の承認が必要」は、
  承認を得たかどうかが学生ごとに違い、PDFには書かれていない。学生の画面で「承認あり／なし」を聞き、
  答えが入れば判定を確定させる。答えがなければ算入せず要確認。
  判定側は `requires_approval` / `approved` として既にできているが、**答えを書き込む画面がまだない**。
  聞く場所は、承認が要る科目の行そのもの（履修登録の一覧と履修計画の画面）に
  「指導教員の承認あり／なし／未回答」を置く。既定は未回答＝要確認。
  実績側は `student_courses.approval_confirmed` に入る。
  **履修予定側には欄がないので足す**（`planned_courses` にマイグレーション）。
  予定に答えられないと、承認が要る科目を計画に入れた学生の見込み判定が永久に要確認のままになる。
- **判定対象外と決めたものは保留。** 外国人学生の特例は要確認のまま。誤って「卒業できます」とは出さない。

## 決めた形（作り）

### 1. 判定ロジックをデータにする — 規則の型は7つだけ

いちばん大きい変更。`CommonChecks` / `SpecialistChecks` / `Evaluation#basic_checks` / `total_check` に
書いてある2024年度向けの規則を、全部データへ移す。

**JSONに任意の式を書けるようにはしない。** 型を7つに閉じ、コードがその7つだけを解釈する。
型が増えるのはコードを変えるときだけ。知らない型が入っていたら、その規則は**充足とせず要確認**にする。

| 型 | 何を見るか | いまのどこ |
|---|---|---|
| `credit_sum` | 指定した区分の合計が n 単位以上 | `CreditCheck`（共通教育の各区分、専門必修の各区分、専門選択、総単位） |
| `all_required` | `required: true` の科目をすべて修得。科目数と単位合計も併せて照合する | `SpecialistChecks#mandatory_check` |
| `one_of_paths` | 役割の組（path）のうち、どれか1つを丸ごと満たす | `RoleCheck`（日本語・指定英語・微分積分・物理） |
| `grouped_max` | 区分を科目番号の接頭辞でグループ分けし、最大のグループが n 単位以上 | `SpecialistChecks#fusion_check`（同一提供コースから4単位） |
| `any_of` | 下に並べた条件のどれか1つを満たす | `CommonChecks#foreign_language_check`（外国語の二択） |
| `cap` | ある区分の算入を n 単位で打ち切る（判定ではなく集計時の加工） | `Ledger#apply_natural_cap`（自然系2単位） |
| `exclude` | 区分、または区分×提供元 を算入対象外にする | `Catalogue#exclusion`（`excluded`、自コース提供の工学融合） |

`any_of` の下に置けるのは `credit_sum` / `grouped_max` と、それらを並べた `all_of` だけ。入れ子は2段まで。
これで外国語の二択（英語12、または 英語8 かつ 同一外国語4）が書けて、それ以上は書けない。

**`all_required` は期待する科目数と単位合計を持つ。** いまの `mandatory_check` は
「必修が31科目でなければ要確認」という歯止めを持っている（`specialist_checks.rb:30`）。
この歯止めを型から落とすと、科目表の読み落としで必修が1科目消えたときに黙って充足になる。
アンチゴールそのものなので、`expected_course_count` と `required_credits` を規則に持たせ、
実際の科目表と食い違ったら判定のたびに要確認にする。取り込み時の機械的検査（後述§4）は
保存した時点のデータにしか効かないので、判定時の網はこちらに残す。

`one_of_paths` は path が1つなら「指定科目すべて」になるので、日本語（1科目）と指定英語（2科目）も
同じ型で書ける。いまの `RoleCheck` がすでにこの形。

**要確認の伝わり方は今のまま。** 規則が参照する区分に未確定の科目があれば `needs_review`。
`grouped_max` のグループ欄（提供コース、言語）が空の科目が算入されていれば要確認
（いまの `inspect_provider` / `inspect_language` を規則から引くように一般化する）。
接頭辞でグループ分けするので、提供元が「未確認」になる経路はなくなる。

### 2. データの形

`format_version: 2`。`Catalogue` の定数が持っていたものが全部ここに来る。

```json
{
  "format_version": 2,
  "faculty_name": "工学部",
  "department_name": "工学科 知能情報コース",
  "department": "intelligent_informatics",
  "admission_year": 2025,
  "title": "2025年度入学 琉球大学工学部工学科 知能情報コース",
  "sources": [{ "id": "handbook_2025", "title": "...", "pages": "3・9-11" }],

  "categories": [
    { "key": "course_required", "label": "コース専門科目（必修）", "counts_toward_total": true },
    { "key": "excluded",        "label": "卒業算入対象外",         "counts_toward_total": false }
  ],

  "roles": [{ "key": "calculus_st_1", "label": "微分積分学Ⅰ（理工系）" }],

  "rules": [
    { "id": "common_total", "type": "credit_sum", "label": "共通教育の合計",
      "categories": ["foundation", "liberal_arts", "first_language", "second_language", "health"],
      "required_credits": 34, "source_page": "3", "detail": "" },

    { "id": "foreign_language", "type": "any_of", "label": "外国語の選択経路", "source_page": "3",
      "options": [
        { "type": "credit_sum", "categories": ["english"], "required_credits": 12 },
        { "type": "all_of", "conditions": [
            { "type": "credit_sum", "categories": ["english"], "required_credits": 8 },
            { "type": "grouped_max", "category": "foreign_language",
              "group_by": "number_prefix_hundreds", "required_credits": 4 }]}
      ]},

    { "id": "required_all", "type": "all_required", "label": "専門必修をすべて修得",
      "expected_course_count": 69, "required_credits": 69, "source_page": "9" },

    { "id": "natural_cap", "type": "cap", "category": "natural", "credits": 2, "source_page": "10" },

    { "id": "own_fusion", "type": "exclude", "category": "fusion",
      "number_prefix": "知能",
      "reason": "自コース提供の工学融合科目は登録・算入不可", "source_page": "10" }
  ],

  "courses": [
    { "key": "知能103", "number": "知能103", "name": "離散数学", "credits": 2,
      "category": "course_required", "required": true,
      "language": null, "roles": [], "source": "handbook_2025", "source_page": "9",
      "review_reason": null, "requires_approval": false, "selectable": true }
  ]
}
```

`courses` の各欄の意味はいまのまま。`category` が `categories[].key` を指すようになる点と、
`requirements`（`english_roles` などの固定キー）が `rules` の `one_of_paths` に吸収される点だけが違う。

**科目のキーは科目番号そのもの。** AIに英語のキーを発明させない。科目番号はPDFに印字されていて
原本と照合でき、`工共100` / `知能103` / `機械990` のように接頭辞が提供元を表す。

2024年度の既存の英語のキー（`programming_practice_1` など）も科目番号に置き換える。

**開講されている科目には、必ず科目番号が付いている。** 提供科目表に行がある科目は、
共通教育も専門も例外なく番号を持つ（人／社／自／総／琉／健／外／C／先／転／工共／知能／
機械／エネ／電気／電情／社基／建築／全教）。番号は琉球大学全体の付番なので、
他学部の便覧でも同じように使える。

例外に見える2件は、科目に番号がないのではなく、**便覧の中で表どうしが食い違っている**もの。
2024年度の分類表は「知能情報特別講義Ⅰ～Ⅵ」と書いているのに、提供科目表には
知能491〜494（Ⅰ〜Ⅳ）しかなく、Ⅴ・Ⅵはどこにも行がない。手で入れたJSONに2件あるのは、
分類表が名前を挙げている科目を拾ったため。これは原本の食い違いなので、
キーを作って済ませるのではなく、**食い違いとして要確認に出す**（§4に検査を足す）。

### 2-2. キーは持たず、科目番号と入学年度から引く（`courses.curriculum_key` を落とす）

いま `courses.curriculum_key` にはDB全体で一意の索引が張ってある（`db/schema.rb`、`app/models/course.rb`）。
同じ「工共100 工学基礎演習」が2024年度の便覧と2025年度の便覧で別のキーを持つと、1行の `Course` に
2つのキーは乗らない。`Course` を年度ごとに増やせば、時間割取り込みが `(course_number, name)` で
引き当てている同一性（`app/models/timetable_upload_row.rb`、`lib/timetable_import/importer.rb`）と
`course_offerings` の紐付けが崩れる。

**キーを保存するのをやめ、科目番号から引く。**
どの便覧を見るかは学生の入学年度が決めている（`StudentWorkspace#load_workspace`）。
年度が便覧を選び、科目番号がその中の行を選ぶので、`Course` にキーを持たせる必要がない。
対応表のテーブルも要らない。

- `courses.curriculum_key` と、その一意索引を落とす。
- 判定は `その学生の便覧の科目表[course.course_number]` で引く。
  通り道は `StudentCourse#assessment_entry` と `StudentWorkspace#planned_entry` の2か所。
- 便覧のJSONの `key` 欄は残すが、中身は科目番号そのもの。`Catalogue` と `Ledger` は触らずに済む。
- 同じ科目番号の `Course` が複数あっても壊れない。`EntryNormalizer` の
  「同一科目の複数記録で単位数が一致しない」検査がそのまま効いて要確認に倒れる。
  `courses.course_number` に一意制約は張らない（時間割取り込みが `(course_number, name)` で
  行を作るため）。
- 読み間違いの出方も安全側。AIが科目番号を1文字読み違えれば、その科目は便覧の行に当たらず、
  「科目の正規キーを科目表と照合できない」で要確認になる。黙って別の区分に入ることはない。

**これに伴って直すもの**

- `db/demo_enrollments.json` の `course_key` を科目番号に置き換える。48件すべて科目番号を持っているので
  機械的に置換できる。`DemoData#import_courses` も `course_number` で引くようにする。
- **自由入力計画科目**（学生が便覧にない科目を計画に打ち込むもの）は、いま
  `curriculum_key` に `custom:<区分>:<乱数>` という文字列を入れて区分を埋め込んでいる
  （`plan_courses_controller.rb:65`、`student_workspace_helper.rb:59,75`）。
  `curriculum_key` を落とすので、`courses` に `custom_category` 欄を足してそちらに移す。
  文字列に意味を埋め込むのをやめる。
- 分類表にしか名前がない科目（2024年度の「特別講義Ⅴ・Ⅵ」）は、どの `Course` とも突き合わない。
  どちらも `credits` が空で `review_reason` が付いており、いまでも要確認になるので、
  判定結果は変わらない。

### 3. 読み取り（AI）

- **1ページ = 1リクエスト。** そのページの画像（`gs -sDEVICE=png16m -r150`、取り込み確認画面と同じ）と、
  そのページのテキスト（`gs -sDEVICE=txtwrite`）を一緒に送る。
  便覧の表は2段組で、テキスト抽出だけだと縦書きの見出しが行に混ざり単位の数字がちぎれる。
  画像がないと区分の線が読めない。両方送る。
- **2種類のプロンプト。** 要件表用と科目表用。科目表のプロンプトには、先に確定した区分の一覧を渡す。
  これをしないと、ページごとに違う区分名が返ってくる。
- 出力はJSON Schemaで縛る。
- **窓口は1クラス。** `CurriculumReader::Reader` だけがAPIを呼ぶ。プロバイダは `CurriculumReader::Gemini`
  のような1クラスに閉じる。差し替えるときに触るのはそこだけ。
- **既定は Gemini（Google AI Studio）の無料枠。** PDFのページ画像をそのまま扱えて、
  カード登録が要らない。本番も無料枠のまま運用する。
- APIキーは環境変数から。**キーがなければ読み取りボタンを出さず、同じ画面が手入力の画面として動く。**
  無料枠が止まっても、いまより悪くはならない。
- 429 と 5xx は指数バックオフで数回だけ再試行する。それでも駄目ならそのページは「未読取」として残し、
  他のページの結果は捨てない。人が手で埋められる。
- **ページごとに下書きを保存する。** 日次の上限に当たって途中で止まっても、確認済みの分は消えない。
- **ジョブ基盤は足さない。** 読み取りは画面から1ページずつ投げ、1リクエストで1ページを読んで保存し、
  Turbo でそのページの行だけ差し替える。10ページを1回のリクエストで回そうとするとタイムアウトする。
  `app/jobs` は空で、本番のキューも未設定（`config.active_job.queue_adapter = :async`）なので、
  ここでキューを導入すると設計の主題から外れた作業が増える。
  途中で閉じても、読んだページは保存済みで、続きから投げ直せる。
- HTTPは標準の `net/http` で足りる。gemは足さない。

**外に出すもの。** 便覧は大学が公開しているPDFなので、無料枠が送信データを学習に使う条件でも送ってよい。
**学生の履修・成績データはAPIに一切送らない。** 送るのは便覧のページ画像とテキストだけ。

### 4. 機械的な突き合わせ（AIには聞かない）

AIに自己申告させても当てにならない。読み取った結果に対して、Rubyで決まった検査をかける。
引っかかった行・規則は要確認で出す。

1. 科目番号の重複。
2. 区分ごとの科目数・単位合計を、要件表の数字と突き合わせる（「必修31科目57単位」など）。
3. `required: true` の科目の単位合計 ＝ 要件表の必修単位。合わなければ両方を要確認。
4. 規則が参照している区分が `categories` にない／どの科目も属していない。
5. 区分ごとの必要単位の合計が、卒業算入の総単位を超えている。
6. 区分のなかで科目番号の接頭辞が他と違う科目（モックの「知能993」のケース）。
7. `source_page` が空の科目・規則。
8. **分類表に名前があるのに、提供科目表に行がない科目。** 2024年度の
   「知能情報特別講義Ⅴ・Ⅵ」がこれ。原本の中の食い違いなので、黙って捨てずに人に見せる。
9. 提供科目表に行があるのに科目番号が読めなかった科目。読み取りの失敗なので、
   そのページを読み直すか手で埋める。

### 4-2. 科目番号から区分を推定し、AIの読み取りと突き合わせる

科目番号の接頭辞と百の位は、区分・提供元・言語をかなりの範囲で決めている。
これはAIに聞かずに計算できるので、**読み取り結果に対する独立した第二の意見**として使う。
2024年度の482科目で実測した結果が下。

**共通教育は接頭辞だけで決まる（251科目、例外なし）**

健→健康運動系、人→人文系、社→社会系、自→自然系、総→総合科目、C→キャリア、
琉→琉大特色・地域創生、先／転→専門基礎。

**英語かどうかは百の位で決まる。言語そのものは決まらない（71科目）**

外1xx→英語(14)。外2xx→ドイツ語(11)、外3xx→フランス語(11)、外4xx→スペイン語(11)、
外5xx→中国語(11)、外6xx→朝鮮語(5) までは百の位と言語が1対1。
**しかし外7xx(8科目)はインドネシア語2・タイ語2・ラテン語2・ロシア語2の4言語が同居している。**

つまり番号から言語は出ない。百の位で括ると、インドネシア語2単位＋タイ語2単位の学生が
「同一外国語4単位」を満たしたことになり、英語8＋外国語4の経路で誤って充足する。
アンチゴールそのものなので、**言語は科目の `language` 欄で持つ**。
取り込み時に番号から推定して埋め、確認画面で人が承認する（§4-2 の「第二の意見」と同じ扱い）。
`grouped_max` は、工学融合では科目番号の接頭辞で、外国語では `language` 欄でグループ分けする。

**提供元は接頭辞と1対1（例外なし）**

機械→mechanical、エネ→energy、電気→electrical、電情→electronics、社基→civil、
建築→architecture、知能→自コース。工学融合38科目がきれいに割れる。

**専門の区分は番号では決まらない（81科目）**

工共と知能は、必修・コア・アドバンスト・関連・工学融合にまたがる。
百の位を足しても分かれない（工共1xx が related/required_comprehensive/required_math/required_core、
知能2xx が required_core/required_research/advanced/… など）。
区分は便覧が決めることで、番号に入っていない。ここはAIと人が決める。

**設計に入れること**

- **`provider` の欄をなくす。** 接頭辞がそのまま提供元なので、AIに英語のコース名を
  発明させる必要がない。工学融合の `grouped_max` は科目番号の接頭辞でグループ分けし、
  `exclude` の「自コース提供の工学融合」も接頭辞で書く。接頭辞と提供元は例外なく1対1。
- **`language` の欄は残す。** 番号から言語は出ない（外7xx に4言語が同居）。
  取り込み時に番号から推定して埋め、確認画面で人が承認する。
  外国語の `grouped_max` はこの欄でグループ分けし、欄が空の科目が算入されていれば要確認にする。
- **区分の推定を突き合わせに使う。** 読み取った科目表から
  「(接頭辞, 百の位) → 区分」の対応を集計し、1つの区分にしか現れない組み合わせを規則とみなす。
  その規則から外れる科目を**不一致**として出す。
  2024年度なら482科目中401科目がこの検査にかかり、残り81科目は「番号では決まらない」と出る。
  対応表はコードに持たず、読み取った科目表から毎回作る。区分の名前は便覧ごとに違うので、
  固定の表を持つと2024年度専用に逆戻りする。
- **科目表の確認画面は、不一致の行を先頭に出す。** 484行を1行ずつ見るのではなく、
  まず数十行の不一致を見れば済む。モックで示した「知能993が工学融合なのにコース専門として
  読まれた」は、知能99xが工学融合にしか現れない接頭辞なのでここで引っかかる。

この検査は、いちばん怖い間違い（区分の取り違え）に対して、AIとは別の根拠で意見を出す。
番号の付け方は琉球大学全体の決まりなので、他学部の便覧でも同じように効く。

### 5. 置き場所

いまは `config/curricula/<department>/<year>.json` をファイルから読んでいる。
事務の人が画面から保存するので、ファイルには書けない（コンテナ、Kamal）。

- 確定した便覧は **DBの `curricula`** に置く。本文は `jsonb`。
- **コースのマスタは作らない。学生から便覧への外部キー1本で足りる。**

  コースの指定が要る場面は2つしかない。(1) 管理画面で保存する便覧がどれかを決めるとき、
  (2) 学生をどの便覧で判定するか決めるとき。

  (2) はいまコースを見ていない。`CurriculumRepository.find` の呼び出しはアプリ全体で2か所
  （`StudentWorkspace#load_workspace`、`DemoData`）で、どちらも `DemoAccount::DEPARTMENT` という
  定数を渡している。学生の `department_id` はデモ用の架空の学科を指していて、判定には使われていない。
  コースを表すはずの `programs` テーブルは作られも参照もされていない。

  なので、**`students` に `curriculum_id` を足す**。これが (2) の答え。
  `departments` も `programs` も触らない。学部・学科・コースのモデリングを整えるのは別の作業。

  - `StudentWorkspace#load_workspace` は `@student.curriculum` を読む。
    `CurriculumRepository.find(department:, admission_year:)` は要らなくなる。
  - 便覧が紐付いていない学生は判定しない。既存の `show_setup` の経路でそう出す。
  - **学生の便覧は明示的に決める。** 新しい便覧を保存しても、既存の学生が勝手に
    別の便覧で判定され直すことはない。これはアンチゴールへの備えでもある。

- (1) のために、`curricula` 自身に識別子を持たせる。`slug`（`intelligent_informatics` のような文字列）と
  `admission_year` で一意。これはコースのマスタではなく、便覧を二重に登録しないための鍵。
  表示用に `faculty_name`・`department_name` を文字列で持つ（「工学部」「工学科 知能情報コース」）。
  管理画面の選択肢は、既にある便覧の `slug` と、新しく打ち込む `slug` から作る。
- `CurriculumRepository.find(department:, admission_year:)` は呼び口を変えず、中でDBを見るようにする。
  パス検査と symlink 脱出の防御は不要になる。
- `config/curricula/*.json` は **seedの入力**に降格する。2024年度のファイルは残し、
  seedと回帰テストの両方で使う。
- **取り込み途中のものも `curricula` の行。取り込み用のテーブルは作らない。**

  下書きと完成品は同じ形（便覧のドキュメント）なので、分ける理由がない。
  `timetable_uploads` → `courses` / `course_offerings` は下書きの行と出来上がりで形が違うので
  分かれているが、ここは当てはまらない。

  「確認中の便覧で学生が判定される」ことは、`students.curriculum_id` が防いでいる。
  下書きの行には学生が誰も紐付いていないので、判定の対象にならない。
  途中でやめたければ行を消す。

  `curricula` が持つもの:

  - `slug` / `admission_year` / `faculty_name` / `department_name`
  - `document`（jsonb。便覧そのもの。`categories` / `roles` / `rules` / `courses`）
  - `published_at`（未公開なら `null`）
  - 下書きのときだけ使う `source_filename` と `pages`
    （ページ番号・種別・読み取り状態のjsonb。途中で止まったとき続きから投げ直すため）

  - 一意索引は**公開済みの行だけ**にかける（`(slug, admission_year) where published_at is not null`）。
    公開済みの2025年度を残したまま、2025年度を読み直せる。
  - `students.curriculum_id` が指せるのは公開済みの行だけ。検証で縛る。
  - 公開するときに、`confirmed` とページの一覧は落とす。`review_reason` は落とさない
    （公開後も判定で要確認を出すのに使う）。
  - **公開済みの便覧は直接編集しない。** 直すときは複製して下書きにし、確認して公開し、
    その年度の学生の `curriculum_id` を付け替える（1本のUPDATE）。
    公開済みの行をその場で書き換えると、学生が編集途中の便覧で判定される。

  確認チェック（`confirmed`）は科目1件ずつ、`document` の該当箇所だけを `jsonb_set` で更新する。
  Rubyで全体を読んで書き戻すと、続けて押したときに取りこぼす。
- ページ画像は `storage/curricula/<id>/p<n>.png`。下書きを捨てたとき・公開したときに消す。

### 6. 画面も便覧データから描く

- `StudentWorkspaceHelper::PLANNER_GROUPS` — 「1. 共通教育 30」「3. 専門必修 57」という4章の構成。

- `PlansHelper::PLANNER_SUBTOTALS` — 3行にまたがる「内数22単位」の小計。
- `DashboardMetrics::GRADUATION_CREDITS = 130` と `CHECK_DRIVEN_ROWS`。

集計する区分は別々。導出しようとすると、導出の規則のほうが `display` そのものより複雑になる。

**誰が埋めるか**

- **2024年度** — 変換スクリプトが `PLANNER_GROUPS` と `PLANNER_SUBTOTALS` をそのまま写す。
  AIを通さない。章・行・ID・文言が1つも変わらない。

- 要件表の確認画面で、章と行の並びを直せるようにする。

**突き合わせに足すもの（§4）**

- `check_ids` が指す規則が存在すること。
- `categories` が指す区分が存在すること。
- 行の必要単位が、チェックが1つだけのとき、その規則の必要単位と一致すること。

  どの行にも出てこない区分の科目は、計画表にも内訳にも出ず、学生から見えないまま消える。
  アンチゴールそのものなので、ここで止める。

**画面側ですること**

- `PLANNER_GROUPS` / `PLANNER_SUBTOTALS` / `CATEGORY_LABELS` / `GRADUATION_CREDITS` /

- `app/views/requirements/show.html.erb` は、便覧の `display` と `rules` を描く
  **読み取り専用**の画面に置き換える。
  **学生が要件を編集できる画面は作らない。** 要件を直すのは、同じ画面の取り込みの側の仕事。
  いまの441行は何も保存しない見本なので、置き換えても失われる機能はない。

### 8. 2024年度を壊していないことの確かめ方

- **先に現状を記録する。** 作り替えに入る前に、実物の `2024.json` と何通りかの学生データで
  `GraduationAssessment` を走らせ、`Snapshot`（全体のステータス、算入単位、各チェックのID・ステータス・
  算入単位・必要単位・不足科目）をフィクスチャとして保存する。
- いまの `2024.json` を新形式へ変換する一度きりのスクリプトを書く。
- **合格条件は、変換後の2024年度がそのフィクスチャと一致すること。**
  チェックIDは `required_all` / `elective_inner` / `general_subtotal` / `fusion_provider` /
  `basic_total` / `calculus` / `physics` などがそのまま使われるよう、変換後JSONで**現行のIDを維持する**。
  これらのIDは画面側からも引かれている（`app/helpers/student_workspace_helper.rb` の `check_ids` など）。
- 既存の `test/services/graduation_assessment_test.rb` は、テスト内で組み立てているドキュメントを
  新形式に書き直す。アサートしているID・ステータス・単位は変えない。
  `detail` の文面はデータ由来になるので、変換後JSONに同じ文面を入れる。
- そのうえで、読み取りの精度の物差しとして、2024年度のPDFをAIに読ませ、
  手で入れた484科目のJSONと差分を取る。答え合わせが無料で手に入る。
  差分の大きさは、確認画面でどれだけ人の手が要るかの見積もりになる。

## 他学部・他学科にどこまで通用するか

「他コース・他学部の便覧も同じ画面から入れられる」はゴールだが、確かめたのは工学部の2冊だけ。
どこまで言えて、どこから言えないかを分けておく。

**作りとしては、コースや学部に依存するものは残らない**

区分の語彙、必要単位、章立て、区分の和名、提供元のグループ分け、除外、上限、
卒業総単位。これらは全部データになる。`Catalogue::PROVIDERS`（工学部の6コース）も
`Catalogue#exclusion` の「自コース提供の工学融合」も消える。
学部・コースは `curricula` の文字列で、`departments` にも `programs` にも縛られない。
科目番号は琉球大学全体の付番なので、他学部の科目でもそのまま鍵になる。

**規則の7つの型は、工学部の2冊に足りるぶんしかない**

型を7つに閉じたのは、何でも書けるJSONにしないため。裏返すと、2冊に出てこなかった形は書けない。
思い当たるものだけでも:

- 単位数ではなく**科目数**での要件（「この区分から3科目以上」）
- **年次の条件**（「2年次までに○○を修得」）
- **成績の条件**（GPA、「可以上」）。`student_courses.grade` はあるが判定は見ていない
- **群から選ぶ**（「A群・B群・C群のうち2群から各4単位」）。`any_of` は「どれか1つ」までで、
  「3つのうち2つ」は書けない
- **区分をまたぐ上限**（`cap` は1区分ずつ）
- `grouped_max` のグループ分けに使えるのは科目番号の接頭辞だけ。
  番号に表れない軸（担当教員、実習先など）では分けられない

これらが要る学部の便覧は、型を1つ足すまで通らない。足す作業は小さい（規則のクラス1つと
スキーマ1行）が、コードを変える作業であって、画面からはできない。

**ただし、通らないときに間違った判定は出ない。**
知らない型・解釈できない規則は、充足にせず必ず要確認にする（§1）。
「この学部はまだ対応していない」が「卒業できます」になることはない。

**運用で先に効いてくるのは、共通教育の重複**

共通教育の約250科目は全学で共通だが、便覧ごとに科目表を持つので、
学部が増えるたびに同じ科目を読み直し、同じ確認作業をすることになる。
2冊なら気にならないが、10学部分では効く。
他の便覧から共通教育の部分を複製する仕組みが要るだろう。今回は作らない。

## 残る制約

- **認証がない。** 取り込みは学部の事務の人が使うものだが、置き場所は学生も開ける
  `/requirements` になる。いまのアプリは固定のデモアカウントで、`LocalAccessOnly` により
  ローカルからしか開けない（`app/controllers/concerns/student_workspace.rb:23`）ので、
  当面は誰にも見えない。
  **認証が入ったら、取り込みのフォームと確認画面は学生から隠す必要がある。**
  講義登録の時間割取り込みがまったく同じ状態なので、そのときに2つまとめて片付ける。
  **事務の人が実際に使えるようになるのは、認証が入ってから。** これはこの設計では解かない。
- **無料枠は提供側の都合で変わる。** 年1回しか動かさないので、「使おうとしたその日に動かない」という
  形で出る。備えは2つだけ：窓口を1クラスに閉じて差し替えられるようにすること、
  APIが使えなくても同じ画面で手入力できること。
- **読み取りの精度は測ってから決める。** 無料枠のモデルが2024年度の答え合わせでどれだけ外すかは、
  やってみるまでわからない。外しが多ければ、確認画面の負担が「手入力より少し楽」程度に留まる可能性がある。
  それでも誤判定にはつながらない（読み取り結果は必ず人が確認してから保存される）。
- 便覧PDFは大学が公開しているものなので、2024年度は既にリポジトリにある（`docs/kogaku_chinot_y24.pdf`）。
  2025年度も同じ扱いで `docs/` に入れ、2冊とも手元で読み取りを試せるようにする。
  時間割の配当表PDF（個人の資料・リポジトリ外）とは扱いが違う。
  APIを叩くテストはスタブで書く。実物を読ませるのは精度の測定であって、CIでは回さない。
- **デモ学生は2024年度固定**（`DemoAccount::ADMISSION_YEAR`）。2025年度を画面で確かめるために、
  2025年度入学のデモ学生をseedに足す。`DemoAccount` が1人の学生を定数で指している作りなので、
  2人目を足せるようにする必要がある。
- **読み取りは同期で、1ページが最大8分スレッドを1本占有する。** ジョブ基盤を足さない決めなので、
  1ページの読み取りはリクエストの中で終わる。再試行が重なると最悪で約8分かかり、Puma は
  スレッド3本なので、一括読み取りを3つ並べると学生側のリクエストも待たされる。
  **学生が使っている時間に一括読み取りをしない**、という運用で避ける。年1回の作業なので割に合う。
  画面側は10分で `AbortController` が表示を戻すが、サーバ側の読み取りは走り続けて結果を書く。
- `gs` は時間割の取り込みで既に必要なので、依存は増えない。

## 作り手に委ねること

- 7つの型それぞれの、規則オブジェクトとしての実装の切り方（1クラス1型か、`CreditCheck` の拡張か）。
- 読み取り結果のJSON Schemaの具体。
- 便覧のページの指定の仕方（一覧にチェックを並べるか、ページ範囲を打たせるか）。
- バックオフの回数と待ち時間。
