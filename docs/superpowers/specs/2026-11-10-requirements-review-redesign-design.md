# 要件表の確認画面の作り直し 設計

2026-11-10 / 対象ブランチ: `feature/curriculum-import`

## なぜ作り直すのか

便覧のPDFから読み取った卒業要件を、公開前に人が見て直す画面(`/curricula/:id` の「要件表の確認」)が、**確認に使えない**。

ユーザーの言葉: 「編集画面の項目が多すぎて、確認するのがほぼ不可能でした」。

直前の作業で、畳まれた `<details>` の中に誤読が隠れるのを嫌って全部を常時表示にした。その結果、1行につき「名前・必要単位・副題・必要単位が空のときの表示・確認する規則のid・並び(小さい順)・2つのチェック・23個の区分チェック」が常に並ぶようになった。共通教育の章だけで4行あるので、章1つで100近い入力欄が出る。誤読は見えるようになったが、人がそれを見つけられる状態ではなくなった。

PDFと突き合わせるときに実際に目で追うのは **必要単位数・科目名・対象科目・修了要件** の4つ。いま画面を埋めている他の項目は、その邪魔をしている。

## 目標

- 便覧のPDFを横に置いて、章→行の順に上から目で追えること。1行が画面の1行に収まること。
- 判定の数字を決める値が、畳まれた中に隠れないこと。見えるか、開く場所が明示されていること。
- アプリの中だけの名前(規則のid)を、人が打たされないこと。
- 「何単位以上・何単位以下」を、どの決まりでも同じ書き方で設定できること。

## 目標でないもの

- 科目表(科目の一覧)の確認画面は変えない。別の画面で、別の作業。
- 判定エンジン(`GraduationAssessment`)の判定結果を変えない。同じ便覧なら、作り直しの前後で学生に出る数字は同じであること。
- 公開済みの便覧の形(`PublishedDocument` が通す欄)を減らさない。既存の2024・2025年度の便覧がそのまま読めること。
- 見た目をmainの「卒業要件ルールビルダー」のモックに一致させること。当初はモックの項目を埋める形を想定していたが、下記のレイアウトの方が見やすいと判断したので、そちらを採る。
- 学生に出る画面(`/requirements`・ダッシュボード・履修計画)を変えること。確認画面だけの作り直し。

## 失敗とみなすもの(アンチゴール)

- 項目を減らした結果、判定の数字を決める値が画面のどこにも出なくなること。直前のレビューで `number_patterns` がこれに当たり、Criticalとして直したばかり。**減らすのは「人が打つ欄」であって「人が見る値」ではない。**
- 「触らずに保存しても何も変わらない」が壊れること。この不変条件は既存のテストが守っており、作り直しでも守る。
- 同じ値を2か所から送ってしまうこと(同名パラメータの重複)。
- 学生に既に出ている文言(「内数22単位枠」など)が、画面を開いて保存しただけで書き換わること。

## 決まったこと

### 1. 学部・学科・コースのプルダウンは、親の選択に連動させる

親が選ばれていないときは `---------` だけを出す。学科は選ばれた学部の学科だけ、コースは選ばれた学科のコースだけ。

取り込みフォームは `program_fields_controller.js` で既にこの動きをする。**対象選択の画面(`/requirements` の `_selector.html.erb`)が未対応**で、全学部の学科・全学科のコースを `<optgroup>` で並べている。ここを同じ動きにする。

**作りは `program_fields_controller.js` に合わせる**(選択肢は全部 `<optgroup>` で描いておき、Stimulusが親に合わないものを hidden/disabled にする)。この形なら、JavaScriptが動かなくても全選択肢から選べ、学部・学科・コースの入ったURLを直接開いても選択が残る。`_selector.html.erb` 冒頭が約束している「GETで持つので再読込やブックマークで壊れない、JSが無くても動く」を壊さない。

### 2. 1行は画面の1行に収める

行に常時出るのは次だけ:

```
↑↓  ●  [行の名前            ]  [14] 〜 [  ] 単位   科目 249件 ▸   …
        対象： 人文系 ×  社会系 ×  自然系 ×  総合科目 ×  キャリア関係 ×  琉大特色・地域創生 ×   ＋
```

- **対象の区分名は常に出す。** 行の名前と同じでも省略しない(ユーザーの選択)。
- **対象はその場で直せる。** チップの `×` で外し、`＋` で便覧の区分から選んで足す。23個のチェックの並びはやめる。区分は判定の数字を決める値なので、読むだけにはしない(取り違えたまま直せないと、この作り直しの目的が達成できない)。
- **科目は件数だけ出し、押すとその場で開く。** 2024年度は行あたり1件〜249件と幅がある。開いたときは区分ごとに、科目名・科目番号・単位数。1件だけの行は最初から開いた状態でよい。科目は**表示だけ**で、フォームの欄にはしない(249件を欄にすると送信が重くなる。科目を直すのは科目表の画面)。
- 残り(補足・単位の詳しい設定・`credits_from_check`・この行を消す)は右端の `…` を押したときだけ出す。

### 3. 単位は「◯単位以上 〜 ◯単位以下」で統一する

どの決まりも同じ2つの欄を持つ。それぞれ空にすると「制限なし」。

| 書き方 | 意味 |
|---|---|
| `14 〜 (空)` | 14単位以上。上はいくらでも |
| `(空) 〜 2` | 2単位まで。超えた分は卒業単位に数えない |
| `6 〜 6` | ちょうど6単位 |
| `(空) 〜 (空)` | 制限なし(数えるだけ) |

上限の意味は **算入上限**。超えて修得した分は卒業の単位として数えない(ユーザーに確認済み)。履修そのものを禁じる意味ではない。

**「必要単位が空のときの表示」(`required_label`)の欄は残す。** 当初は無くすつもりだったが、`GraduationAssessment::Catalogue` は必要単位が null の行にこの欄が無いと便覧の読み込みを拒む(公開も止まる)。2024年度の3行は既に値を持ち、学生の画面に「内数22単位枠」「3区分計 22単位」「選択全体 37単位枠」として大きく出ている。**勝手に書き換えない。**

ただし下記5のとおり、この3つの値は「大枠に単位を置く場所が無い」ことの埋め合わせなので、枠が単位を持つようになれば人が自分で消せる(消すかどうかは人が決める。学生に出る文言なので画面が勝手に消さない)。欄は `…` の中で、下限の選択とひと続きに見せる:

```
この行に必要な単位（下限）
  ◉ [14] 単位以上
  ◯ この行だけの決まりは無い（上の章の単位に含まれる）   画面に出す言葉 [内数22単位枠]
```

下限が空で言葉も空の行だけ、行の表示に「内数」と出す(文書には書き込まない)。

### 4. 行の中に、さらに決まりを入れ子にできる

2024年度の「教養領域は14単位以上、ただし自然系は2単位まで」は、教養領域の行の内側に `(空) 〜 2 / 対象: 自然系` という決まりを置く形で表す。

入れ子は「いずれかを満たす(OR)」「すべてを満たす(AND)」のバッジ付きで、既存の `one_of_paths` / `any_of` / `all_of` もここに出る(直前の作業で作ったAND/ORの枠をそのまま使う)。

**上限は便覧全体に効くことを、その場に明記する。** `cap` は台帳全体のその区分に掛かる調整で、行や章には閉じていない。教養領域の行の内側に置くのは見つけやすさのためなので、文言は「自然系は**便覧全体で**2単位まで」とする。行の中だけに効く上限という新しい意味は作らない(判定エンジンが変わり、「判定結果を変えない」制約とぶつかる)。同じ区分に2つの行から上限を書こうとしたら、2つめは断る。

### 5. 「確認する規則」をidで指すのをやめる

行から `japanese, english_required` のようなidを打つ形を廃止する。満たし方は行の中に直接書く。idはアプリが裏で振り、人は一度も見ない。

文書(`document`)の形は変えない。`rules[]` と `display.rows[].check_ids` は今までどおり持つが、**画面がその対応を自動で作る**。行に決まりを足せば規則が作られて `check_ids` が繋がり、行を消せばその行だけが指していた規則も消える。自動で振るidは、その行のidから作る(`<row id>_c1` のような形)。`DraftMerge` の読み直しがidを付け替える仕組みと噛むので、実装時に `draft_merge/display_merge.rb` の扱いを確かめること。

#### 行に出る数字と、入れ子の決まりの数字は別物

実データでは、行に出ている数字と判定が使う数字が別の場所にある行がある。`外国語科目` の行は表示12で、判定が見る12は `any_of` の選択肢の中にある。`基幹領域：日本語表現法入門` の行は表示2だが、指す規則は `one_of_paths` で単位の欄を持たない。

**行の `以上〜以下` は `display.rows[].required_credits` だけを読み書きする。入れ子の決まりの数字は、その決まり自身が持つ。** 行の数字を入れ子に書き込んだり、その逆をしたりしない(どの入れ子に書くべきか決められない行があり、判定結果を変える恐れがある)。画面は両方を出すので、人は食い違いを目で見つけられる。既存の突き合わせ(`validation/display_checks.rb` の `required_credits_agree`)は、指す決まりが1つのときだけ両者を比べて警告する。この警告を**複数の決まりを持つ行にも広げる**のは、この作り直しの範囲に含めてよい(別立てのタスク)。

#### 複数の行が同じ決まりを共有している場合 → 大枠が単位を持つ

実データで、2つ以上から指されている決まりは3つある。いずれも「複数のものをまとめた合計」で、**まとめている枠の側に単位を持たせれば解ける**(ユーザーの判断)。

| 決まり | 指しているもの | 単位を持たせる先 |
|---|---|---|
| 専門基礎教育の合計 6単位 | 章「2. 専門基礎教育」と、その中の1行 | **章** |
| 専門選択の合計 37単位 | 章「4. 専門選択科目」と、行「専門科目（自由）」 | **章** |
| 数学基礎選択＋アドバンスト＋関連 22単位 | 3つの行と、小計1つ | **枠**(下記) |

いまのデータは、この置き場所が無いせいで歪んでいる。章「4. 専門選択科目」の中身は実際にはこうなっている:

```
行「数学基礎（選択）」      必要単位なし  表示「内数22単位枠」
行「知能情報アドバンスト」  22単位        表示「3区分計 22単位」   ← 22 が真ん中の行に置かれている
行「知能情報関連」          必要単位なし  表示「内数22単位枠」
行「専門科目（自由）」      必要単位なし  表示「選択全体 37単位枠」
```

3区分で22単位という決まりの置き場所が無いので、22を真ん中の行に押し込み、残りの行に説明文を書いて辻褄を合わせている。「必要単位が空のときの表示」が分かりづらい原因がこれ。

**大枠が単位を持てるようにすれば、この3つの説明文は要らなくなる:**

```
章「4. 専門選択科目」                      [37] 〜 [  ] 単位
   ┌ 枠「数学基礎（選択）・アドバンスト・関連の合計」  [22] 〜 [  ] 単位 ┐
   │   ● 数学基礎（選択）        (空) 〜 (空)                          │
   │   ● 知能情報アドバンスト    (空) 〜 (空)                          │
   │   ● 知能情報関連            (空) 〜 (空)                          │
   └──────────────────────────────────────┘
   ● 工学融合科目               [4] 〜 [  ] 単位
   ● 専門科目（自由）           (空) 〜 (空)
```

この「枠」は新しい概念ではない。**いまの `display.subtotals` がこれ**で、`elective_inner` は既に `row_ids: [elective_math, advanced, related]`・`required_credits: 22` を持っている。画面の外に別立てで置かれているせいで、まとめている対象が見えていなかっただけ。

やること: 小計を、`row_ids` が指す行を囲む枠としてツリーの中に描き、枠自身の `以上〜以下` を持たせる。共有されている決まりの欄は、章なら章、枠なら枠に出し、行には出さない。

`row_ids` が1つの章の中で連続していない小計は枠にできない(2024年度の1件は連続している)。その場合は今までどおり章の後ろに並べ、「この小計がまとめている行」を名前で出す。

### 6. どの行にも属さない決まりの置き場所

2024年度の実データで、章・行・小計のどこからも指されていない規則が5つある。規則の一覧を消すと、これらが画面から消える。**消してはいけない。**

| 規則 | 型 | 置き場所 |
|---|---|---|
| `total` 卒業算入総単位 | credit_sum | 画面いちばん上の「卒業に必要な総単位」の枠。いまは `display.total_credits` という数字だけを出しているので、その決まりも同じ枠に出す |
| `required_total` 専門必修の合計 | credit_sum | 「どの行にも結びついていない決まり」の枠。章に付けたいところだが `display.groups[].check_id` は単数で、専門必修の章は既に `required_all` を指している。配列にするのは「文書の形を変えない」制約に反する |
| `natural_cap` | cap | 教養・総合領域の行の内側の決まり(上記4) |
| `excluded_category` / `own_fusion` | exclude | 「算入しない科目」の枠(下記9)。要件ではなく除外なので、章・行のツリーには混ぜない |

読み取り直後にどこからも指されていない決まりが残った場合も、同じ枠に出す。黙って隠さない。**「決まりを足す」フォームはこの枠の中に残す**(AIが読み落とした要件を人が足す唯一の手段)。

### 7. 決まりが持つ、単位以外の値

規則の一覧を消すので、次の値の置き場所を決めておく。いずれも「人が見る値」。

- **`source_page`(例:「便覧10ページ・PDF11ページ」)は常時表示。** PDFと突き合わせる唯一の手がかりなので、畳まない。
- `label`・`detail`・`review_note` は決まりの `…` の中。`review_note`(`one_of_paths`)は全学生の判定を「要確認」にし、学生の画面に出る値なので、人が外せること。

### 8. 並び替えは矢印で

「並び(小さい順)」の数字の欄をやめ、行の左の ↑ ↓ で動かす。`DisplayEditing#merge_in_order` はidで突き合わせ、送信順で並びを決めるので、DOMの要素を入れ替えるだけで並びが伝わり `position` の欄は要らない。

### 9. 「算入しない科目」を画面から設定できるようにする

いまの除外(`exclude`)は **区分が必須**で、科目番号の接頭辞を任意で足せるだけ。2024年度の2件はこれで書けているが、人が画面から足す手段が無い。

**前提として、他学部の科目はすでに一律で要確認になっている。** 科目表に載っておらず、どの区分の `number_patterns` にも当たらない科目は、算入0で「科目表と照合できないため、分類・同一性の確認が必要」と出る(実際に動かして確認済み)。ここに作るものは無い。

**他コースを一律で要確認にはしない。** 他コース提供の工学融合科目(機械991 など)は、「工学融合4単位」の要件を満たすための科目そのもの。一律にすると、満たせるはずの要件が全員要確認になる。止めるべきは自コース提供の分(知能991)だけで、これは逆向きの条件。

そこで、画面から設定できる除外は次の2つの条件とする(両方書いたときは、両方に当たる科目を除外する)。

| 条件 | 例 | 当たるもの |
|---|---|---|
| 区分 ＋ 提供コース（一致 / 以外） | 区分「工学融合科目」＋ 提供コース「知能」と一致 | 自コース提供の工学融合科目 |
| 科目番号（いくつでも） | 理101・農201 | 名指しの科目 |

```
算入しない科目
  ● 区分 [工学融合科目 ▾]   提供コース [知能 ▾]  ◉一致 ◯以外
    理由 [自コース提供の工学融合科目は登録・算入不可]
  ● 科目番号 [理101 ×] [農201 ×]  ＋
    理由 [他学部の情報系科目は卒業単位に算入しない]
  ＋ 追加
```

**提供コースは科目番号の接頭辞で表す。** 便覧は提供コースの名前を持たないため(`grouped_max` の `group_by: number_prefix` が「提供コース別」と呼んでいるのと同じ扱い)。選択肢は科目表に出てくる接頭辞から作り、どの科目が当たるかを例示する。

**判定への影響:**

- `Rules::Exclude` を、区分を必須にしない形に広げる(科目番号だけの除外を書けるようにするため)。条件が全部空の除外は、すべての科目を除外してしまうので断る。
- 区分＋提供コースの除外は、いまの仕組み(科目表に載っている科目に当てる)のままで足りる。
- 科目番号での除外も、科目表に載っている科目に当てるだけなら今のままで足りる。**科目表に載っていない科目(他学部の科目)にも当てたい場合だけ**、`EntryNormalizer` に経路を足す必要がある。これは「要確認」を「算入対象外」に変えるだけの見やすさの改善で、単位は動かない。**分けて後からでもよい。**
- どの変更も単位が増える方向には動かない。2024・2025年度のデータに新しい形の除外は無いので、判定結果は変わらない。

### 10. 小計(`display.subtotals`)は「枠」としてツリーの中に入れる

上記5のとおり、小計は「複数の行をまとめて数える決まり」なので、別立ての節をやめ、`row_ids` が指す行を囲む枠としてツリーの中に描く。枠は章と同じく `以上〜以下` を持つ。`_requirements_subtotals.html.erb` は、この枠に作り替える。

枠の `row_ids` は、囲んでいる行から自動で決まる(人が id を打たない)。枠を外せば、中の行は章の直下に戻る。

## 制約

- **判定結果を変えない。** `test/fixtures/files/graduation_golden_2024.json`(2024年度の実データでの判定結果の固定フィクスチャ)は変えない。変わったら設計か実装が間違っている。
- **既存の不変条件を守る。** 画面を開いて触らずに保存したとき、文書が1バイトも変わらず「人が確認した」印も付かないこと。既存テスト(`触らずに保存しても…`)が守っている。
- **同名パラメータを2か所から送らない。** `review.claim_rule_box?` の仕組みがある。
- **`number_patterns` を画面から消さない。** 区分の欄として直前に追加したばかり。
- 1つのフォーム(`requirements_form`)で章・行・決まりをまとめて保存する今の作り、`RequirementsEdit`・`revision` による競合検出、`DraftMerge` の「人が確認した」印は、そのまま使う。作り直すのは画面(view)と、画面とフォームの間の組み立てだけ。

## 作る側に委ねること

- **上限(以下)を複数区分に掛けたいときの載せ方。** 今の `cap` 型は1つの区分にしか掛からない。`cap` が区分の配列も受けられるように広げるのが素直だと考えるが、`RuleShape`・`Validation`・`PublishedDocument`・判定の各所に触れる。2024・2025年度の実データに出てくる上限はすべて単一区分なので、複数区分の上限は「書けるが警告を出す」程度でも当面は足りる。
- 科目の一覧を開いたときの出し方(その場で展開か、横に出すか)。
